# 多租户 RAG 助手平台 — 产品设计稿（v0.1）

- **状态**：草案（调研沉淀 + 方向对齐）
- **日期**：2026-11-18
- **范围**：本文是「未来产品」的第一份正式设计稿，独立于当前 `enterprise-kb` demo 的技术演进，但复用了 demo 阶段沉淀的检索链路与评估经验。

---

## 1. 产品定位

一个**多租户 SaaS** 的 RAG 助手平台，核心差异化不是「再做一个知识库问答」，而是**把「人本中心评估 + 可解释调参」做成产品的一等公民**，让**非工程师**也能把一个 RAG 助手从「能用」调到「好用」。

### 1.1 一句话定位

> 内置助手模板 + 多租户知识库，配合「上传 PDF → 自动生成评估问题 → 用户简单评分 → 可解释调参建议」的人本中心闭环，让非工程师也能持续优化自己的 RAG 助手。

### 1.2 目标用户

- **开发者个人**：快速搭一个自己领域的助手，愿意花几分钟「评分」换「更好的效果」
- **企业/团队**：私有化部署，知识库敏感，需要「透明、可解释、可回归」的评估体系

---

## 2. 竞品现状与差异化（只看现状，不赌未来）

调研结论：本产品 = **两个成熟品类在交叉点上的融合**，而「交叉点」恰好是两边都做得最薄的地方。

| 模块 | 竞品成熟度 | 本产品策略 |
|---|---|---|
| 多租户 / 知识库 | Dify / FastGPT / RAGFlow 成熟 | table stakes，跟随 |
| 助手模板 | Dify Template Marketplace 已有 | table stakes，跟随 |
| BYO-LLM（自填 API key） | Dify 全覆盖（vLLM/Ollama/OpenAI 兼容 + 5 类模型插件） | table stakes，跟随 |
| 版本对比评估 | Confident AI 成熟（但面向工程师/CI） | 跟随，但做「引导式」 |
| **评分 → 可解释调参建议** | **空白**（AutoRAG-HP 是黑盒自动，无人做可解释） | **技术壁垒** |
| **引导式评估 UX（非工程师）** | **空白**（都假设用户是工程师） | **真护城河** |

**核心判断**：差异化不押在「评估算法」或「私有化架构」上（这些竞品容易追），而押在**「引导 + diff 可视化 + 引导修改」的产品/UX 层**——这是最难被快速复制的。

## 3. 核心闭环（人本中心评估）

### 3.1 冷启动引导流程

```
用户上传 PDF
  → 默认参数解析（chunk / embedding / top-k 取默认值）
  → 自动生成「概括性问题 + 真实召回答案」（种子问题，20–30 个）
  → 用户 listwise 简单评分（点赞/点踩/复制/重新生成，非逐 chunk 打分）
  → 展示评分置信区间（借鉴 ARES 的 PPI 思路）
  → 决定参数是否调整
```

**关键设计原则（来自 Pistis-RAG 的启示）**：
- 用户反馈必须是**低摩擦的 listwise 信号**，不是让用户逐条给 chunk 打详细评语
- 评分后要给**置信区间**，而不是裸分（透明 + 解决样本少时的诚实性问题）

### 3.2 版本 + Golden Case 管理

```
正式发布后，用户在对话里挑选 golden case（真实提问 + 期望答案）
发新版时 → 用旧 golden case 在新版本上回归评分 + diff 对比
  → diff 展示「哪些块的召回丢失/改变了」
  → 提示内容变了 → 引导用户更新 golden case
```

**关键设计（差异化所在）**：版本对比不是给工程师的 CI 报表，而是**给非工程师的「引导式 diff」**——告诉他「这条 golden case 在新版下回答变差了，是因为这段文档被改了，要不要更新这条 golden case」。

## 4. 参数白名单（三档分级）

**设计哲学**：该解释的解释，该让用户选的让用户选，该藏起来的藏起来。不做 Dify 那种「全平铺」让非工程师直接懵。

### 4.1 参数重要性排序（依据 IBM 2505.03452 的统计检验）

跨 5 个数据集高度一致（likelihood ratio test）：

| 排名 | 参数 | 显著性 |
|---|---|---|
| 1 | 生成模型（generative model） | p≈0，碾压性第一 |
| 2 | embedding 模型 | p≪0.001 |
| 3 | top-k | p≪0.001 |
| 3 | chunk size | p<0.001 |
| 5 | chunk overlap | **p=0.35~0.99，基本不显著** |

### 4.2 三档分级

| 档位 | 参数 | 策略 |
|---|---|---|
| **强建议**（离散、证据清晰） | 生成模型、embedding 模型 | 系统主动建议 + 给理由 |
| **用户自滑**（成本/质量权衡） | top-k、chunk size、是否 rerank | 说清权衡，让用户滑 |
| **用户自选 / 不暴露** | 向量库（自选）、chunk overlap、temperature | 不做引导 |

**⚠️ 两条诚实性红线（来自论文间的矛盾）**：
1. 参数重要性是 **dataset-dependent** 的（2505.08445 认为 chunk overlap 重要，2505.03452 认为它基本没用）→ **不能硬编码「最优参数表」，必须基于用户自己上传的数据跑真实评估**
2. 2505.08445 的「naive > semantic chunking」结论可能受其自研 semantic 实现质量影响 → 只借用它的「措辞模板」，不照搬绝对结论

### 4.3 向量数据库（用户决策）

- **不做引导**，让用户自行选择
- 当前仅支持项目里已有的 **Qdrant**（local mode，见 ADR-003）
- 后续新增支持（Chroma / FAISS / Milvus 等），用户可自由切换

## 5. 建议引擎（内部算法）

**结论：不需要重型算法，简单贪心就够。**

- 采用 **Greedy-M（模型优先）顺序**：先生成模型 → embedding → chunk size → top-k（IBM 2505.03452 证明模型优先优于检索优先）
- **不用 MAB**（AutoRAG-HP 的黑盒 bandit 在这里是过度设计，且它不解释）
- 种子问题 **20–30 个就够**（IBM 证明开发集采样 10% 就能跑 HPO，性能几乎不掉）
- 核心难点**不在调参算法**，而在**「为什么建议调这个参数」的可解释性**（AutoRAG-HP 是黑盒，不做解释 → 这是本产品的技术壁垒）

### 5.1 「可解释」的能力边界

- **离散参数**（模型、chunk 策略）→ 好解释：「把 top-k 从 3 调到 5，因为你的问题偏长、召回不全，试了几组后 5 的 faithful 率明显高」
- **连续/组合参数**（压缩比、混合权重）→ 难解释，且 AutoRAG-HP 证明此处**搜索空间退化严重**，精确推荐本身不成立 → **策略：只对离散参数做「强建议」，连续参数做「弱建议 + 让用户自己滑」**

## 6. 多租户架构

- **多租户 SaaS**，内置助手模板（devops / UI 开发等），模板自带「常用知识库内容」做种子
- 用户可**按模板创建**，也可**完全自定义** + 自由上传知识库
- **模型归属（用户决策）**：日常使用 + judge 调用的模型都交给用户决定，用户自填 API key（学 Dify 的 BYO-LLM）
- 私有化部署 + 组织内多租户（企业知识库场景的 table stakes）

---

## 7. MVP 范围（砍骨架，先验证核心假设）

**关键决策**：骨架（模板/知识库/BYO-LLM）都是 table stakes，MVP **先只做「评估闭环 + 引导 UX」这一个核心闭环**，挂载在现有 `enterprise-kb` demo 上验证。

要验证的**最关键假设**：**非工程师愿不愿意用「引导式评估」这个流程**（上传 → 评分 → 收建议 → 确认）。

### MVP 交付物
1. **评估闭环**：上传 PDF → 默认参数解析 → 自动生成种子问题 → listwise 简单评分 → 置信区间展示
2. **建议引擎**：评分 → 可解释调参建议（三档分级 + 措辞模板）
3. **引导 UX**：冷启动引导 + diff 可视化 + golden case 管理

## 8. 已对齐的关键决策（速查）

1. ✅ 多租户 SaaS + 内置助手模板 + 种子知识库
2. ✅ 人本中心评估闭环（评分 → 可解释建议）
3. ✅ 版本 + Golden Case 管理（回归 + diff 对比）
4. ✅ **产品哲学：可解释建议 + 人确认**（不是黑盒自动调参）
5. ✅ **模型归属：用户自填 API key**（judge + 日常调用，学 Dify）
6. ✅ **竞品：只看现状，找改进点**（不赌未来）
7. ✅ **MVP：砍骨架，先做评估闭环 + 引导 UX**
8. ✅ **向量库：不做引导，用户自选**（当前仅 Qdrant，后续扩展）
9. ✅ OpenClaw 技能化先不做
